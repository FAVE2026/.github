Getting started

This organisation is where we keep our projects, track work and review changes. Everyone here has owner access, so we can all manage repositories and organisation settings. Give the others a heads-up before making changes that affect the whole team.

Where to find things

* Repositories: Each project’s files and code. Start with the README inside the repository for setup instructions and project details.
* Issues: Bugs, ideas and tasks. Check what’s already open before adding something new.
* Pull requests: Changes someone wants to bring into the main version of a project. This is where we review and discuss them.
* Projects: Boards for organising work and tracking progress, where we’re using them.
* Settings: Access, integrations and configuration for the organisation or an individual repository.

Making changes

1. Open the relevant repository and read its README.
2. Check the existing issues and pull requests so you don’t duplicate someone else’s work. Assign yourself to the issue or leave a comment saying you’re picking it up.
3. Create a branch from the latest main branch. A branch lets you work on changes separately. Give it a clear name, like fix/login-error.
4. Make your changes and commit them—save them with a short message explaining what changed. If you’re working locally, push them to GitHub.
5. Open a pull request explaining what you changed, why, and how you checked it. Link the relevant issue.
6. Ask another person to review it. Address any feedback and check that any automated checks pass before merging it into the main branch.

Keep each pull request focused on one task so it’s easy to follow.

Working together

Use issues and pull requests to keep useful decisions with the project. If something is agreed in a chat, add a quick note on GitHub too.

Check with the team before deleting or transferring repositories, changing visibility or access, or altering shared settings. Owner access gives us the ability to do these things, but they can affect everyone.

When creating a repository, give it a clear name, choose its visibility deliberately, and add a README explaining what it does and how to use it.

If you’re unsure where something belongs, open an issue in the relevant repository and tag someone.
